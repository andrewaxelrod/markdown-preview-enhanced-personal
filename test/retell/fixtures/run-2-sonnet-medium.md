# Section 7: Specs, ADRs, constitution

## Specs

Keep one living spec per area or feature that represents the current truth. Express changes as deltas that merge into the living spec once they ship — this is the OpenSpec pattern. If you instead use numbered per-feature directories, which is the Spec Kit pattern, add a current-state index so the retrieval subagent has one authoritative place to look.

Avoid having ten isolated per-feature specs with no merged baseline. Nobody reads all ten, and an agent will hallucinate a constraint from one that's already been superseded.

## ADRs

Architecture decision records, or ADRs, live one per file, at a path like docs, adr, followed by a four-digit number and a slug. Each has a stable numeric ID that is never renumbered. Reference them from code using the bare ID at the one or two real decision points only, nowhere else — for example, a comment that just reads ADR-0007. Never include the file path, because that breaks on reorganization, and never paraphrase the decision, because a paraphrase rots silently and nothing can check it against the original. The reader is expected to open the ADR itself.

## Linking code to specs

A file called drift dot lock is the single authority for which code a spec governs, as covered in Section ten. Ordinary source files carry nothing themselves. When code and spec disagree, the spec plus the lockfile wins: the code gets reported as stale, and a human makes the call. An agent should never be allowed to rewrite a spec to match the code.

Markers exist for the one relationship the lockfile cannot express, which is requirement-level granularity, and they go in exactly three places, always as a bare, stable ID with no path and no paraphrase. First, at an ADR decision point, using a marker like ADR-0007. Second, on the smallest stable symbol that enforces a non-obvious acceptance criterion, using a marker that reads "Implements: payments dot refund-window" — this is needed because the lockfile binds spec to symbol, not requirement to symbol. Third, on the acceptance test for that criterion, using "Verifies: payments dot refund-window," ideally as runner metadata where the test framework supports it, otherwise as a comment — the test is where a criterion becomes falsifiable.

Never place these markers in file headers, since that's an unbounded claim of governance nothing can check; also never in ordinary unit tests, generated output, config, migrations, vendored code, dependency-injection wiring, or barrel re-export files. If generated code is itself the contract, as with protobuf stubs, mark the generator input instead. Mirroring your specs directory structure against your source directory structure is a useful discovery hint, but it is not a link — and cross-cutting specs like authentication, money, or idempotency will break that mirroring anyway.

The reasoning for bare IDs: a path breaks on every specs-folder reorganization and duplicates what the lockfile already records; a one-line summary is a paraphrase no tool can check against the actual requirement, so it silently rots. A stable ID, by contrast, survives file moves and gives both agents and humans a high-precision grep target.

The discovery order for an agent holding a file is: first run drift refs against the path, then look for Implements markers within the file itself, then fall back to the root pointer table and the retrieval subagent.

**Declaring IDs.** The format is spec-slug dot requirement-slug, all lowercase, and an ID is never renamed — deprecate it instead if it's no longer needed. Coverage is opt-in per requirement, so items that are context-only don't cause continuous integration to fail. A line reading "Needs: impl, test" must directly follow the requirement's heading with no blank line in between — this is required both by the project's own check-trace script and by OpenFastTrace. As an example, a requirement heading for payments dot refund-window would be followed immediately by "Needs: impl, test," and then prose stating that the system shall reject a refund requested more than thirty days after capture, returning an error code of REFUND_WINDOW_EXPIRED.

In code, the enforcing function would carry a comment reading "Implements: payments dot refund-window" directly above the function that checks whether the number of days between capture and now exceeds thirty, and throws that payment error if so.

For tests, keep the test name itself readable in plain language, and put the ID in runner metadata or a marker comment rather than in the name — unless you specifically want to filter tests by ID using a tool like pytest's dash k flag. In Python, that looks like a decorator reading "verifies, payments dot refund-window" above a test function named something like "test refund on day 31 is rejected." The project's pytest configuration file registers "verifies" as a recognized marker type with a description noting it's for acceptance tests of a spec requirement. In TypeScript, the equivalent is a comment reading "Verifies: payments dot refund-window" above a test that checks the refund-window function throws the expected error message when called on day thirty-one.

**CI gates.** There are three, and all of them are cheap to run. The requirements traceability matrix is a build artifact produced by the third gate; if anyone ever hand-edits that matrix, it means the design has failed. Gate one is a drift check, which catches bound code that changed without its governing spec changing too, as described in Section ten. Gate two is ID resolution: every marker must be a bare ID that resolves to a declared requirement or ADR, and paths, prose, or unknown IDs all cause failure. Gate three is coverage: every requirement that declares "Needs: impl, test" must have at least one Implements marker and at least one Verifies marker.

A script, called check-trace, implements gates two and three and writes out the traceability matrix as a markdown file under the build directory. In broad strokes, here's what that script does. It scans every spec file for requirement headings and their associated Needs declarations, and scans the ADR directory for ADR IDs, building a combined list of all declared IDs. It then defines strict patterns that a marker line must match exactly — the marker has to be the whole comment, nothing else sharing the line — covering the Implements and Verifies comment style, the dot-mark decorator style used in test frameworks, and the bare ADR-number style. It walks through every source and test file with a relevant extension, and for each line that loosely looks like it contains a marker, checks whether it matches one of the strict patterns; if not, that's an error, because the marker isn't a bare declared ID. If it matches, the script checks whether the ID is actually declared; unknown IDs are errors, and known ones get recorded as covered for that kind, implementation or test. It then cross-checks every requirement that declared needs against what was actually found, reporting an error for any that's missing implementation or test coverage. Finally it writes the traceability matrix as a markdown table listing every ID alongside whether it has implementation coverage, test coverage, and its source file, and it exits with a failure status if there were any errors, or prints a success summary otherwise.

**Escalation.** Adopt OpenFastTrace only once a regulator or auditor is genuinely in the loop. Under that scheme, IDs gain a revision suffix, so payments dot refund-window becomes something like "req tilde payments dot refund-window tilde 1," and markers become bracketed tags like "impl arrow req tilde payments dot refund-window tilde 1" and the equivalent for unit tests, with a command called "oft trace" producing the report. Two real-world adopters, JabRef and Eclipse Ankaios, run this in production. The revision suffix is designed to deliberately orphan every marker whenever a requirement changes, forcing a human to re-review each site individually — so only adopt it alongside a firm rule that an outdated-link failure requires an actual human re-read, otherwise agents will simply bump the revision number to make the build pass. There are two adoption footguns to know about: the markdown linter rule that forbids missing a blank line after a heading has to be disabled for spec files, and IDs can't start with a digit, so an ADR about integer cents becomes something like "adr tilde integer-cents tilde 1." If trace integrity needs to be contractually guaranteed, skip comment-based markers altogether and generate language-native requirement constants instead, so that removing a requirement breaks the build outright.

## Should source code link to specs?

No. The link always runs from the document to the code, never the reverse, with ADR IDs as the sole exception.

Here's how each direction is handled. Spec pointing to code: yes, done with a command like "drift link" naming the spec file and the target source symbol, and recorded in drift dot lock. Code pointing to an ADR: yes, but sparingly, using a comment like "ADR-0007: ..." only at the actual decision point, and always as an ID, never as a path. Code pointing to a spec: no — the reverse lookup is done with "drift refs" against the file, or by grepping the lockfile, and the retrieval subagent handles this; the one exception is a stable spec slug, never a path, placed in a module-level docblock, but only when a single module implements a single spec end to end. Root file pointing to specs: only through a pointer table, using directory paths written out in plain text, never as an actual import.

The reasoning: paths rot with every rename, per-file references are exactly the bloat this whole approach is trying to remove, and a spec that governs a file is already discoverable through the lockfile. Keeping the binding in one single lockfile also means continuous integration, humans, and agents are all reading from the same source of truth.

## Constitution

Split constitutional clauses by how enforceable they are. A clause that's mechanically checkable, such as "never run rm dash r f" or "never edit a shipped migration," belongs in a deny rule, a hook, or a continuous integration gate. A clause that requires judgment, such as "prefer composition over inheritance," belongs among five to seven terse imperatives in the root AGENTS dot md file. Rationale and history belong in a separate constitution document, loaded either through a constitution skill or through the retrieval subagent.

A constitution that isn't actually in the agent's context is a constitution the agent will violate. That's the argument for putting the imperatives themselves in the root file, rather than just a pointer to the full document.
